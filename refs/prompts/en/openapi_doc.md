# Задача: документация REST API по спецификации OpenAPI

Ты — эксперт по документированию REST API. Сгенерируй человекочитаемую документацию API на основе артефакта OpenAPI (JSON или YAML) для продукта {repo_name}. Только то, что есть в спецификации.

## Входные данные
- Продукт (репозиторий): {repo_name}
- Артефакт: {artifact_name}
- Ранее сгенерированная документация (для согласованности): {previous_content}
- Исходная спецификация OpenAPI:
{content}

## Язык вывода
Русский — основной; английский — для endpoint-ов, HTTP-методов, кодов состояний, схем и полей.

## Границы доказательности
Анализируй ТОЛЬКО предоставленную спецификацию (см. единые правила верификации). Не выдумывай операции, параметры и поля. Сохраняй точные имена путей, операций, схем и полей и их порядок из артефакта. Если данных недостаточно — укажи явно.

## Порядок работы (внутренне)
1. Извлеки `info`, `servers`, `security`.
2. Пройди по `paths` в исходном порядке; для каждой операции собери параметры, request body, ответы.
3. Пройди по `components/schemas`; для каждой схемы собери поля, required, enum, default, ограничения.

## Контракт вывода
Markdown. Разделы:

## 1. Обзор API
Base path / `servers`, версия (`info.version`), назначение, форматы (например, application/json).

## 2. Аутентификация и авторизация
Схемы security (Bearer, ApiKey, OAuth2, OpenID Connect), где передаются учётные данные, требования к токенам/ключам.

## 3. Эндпоинты
Таблица по операциям (path + method):
| Метод | Путь | Summary | Описание | Параметры | Тело запроса | Ответы |
|-------|------|---------|----------|-----------|--------------|--------|

Указывай типы и обязательность параметров, content-type тела, коды ответов и связанные схемы.

## 4. Модели данных (Schemas)
Для каждой схемы — таблица полей:
| Поле | Тип | Обязательное | Формат | Описание | Пример |
|------|-----|--------------|--------|----------|--------|

Отмечай required, enum, default, ограничения (minLength, maxLength, pattern, minimum, maximum).

## 5. Примеры
Примеры запросов/ответов для ключевых операций (из `example`/`examples`), в блоках кода. Структуры данных описывай таблицами, а не сырым JSON.

## 6. Зависимости между операциями
Логические группы, связи (создание → получение по id), pagination/фильтрация/сортировка, если применимо.

## Профили контекста
- Large: полностью все операции и схемы с таблицами и примерами.
- Small: обязательны «Обзор», «Аутентификация», таблица эндпоинтов; детальные таблицы полей — для ключевых схем, остальные перечисли списком. Сохрани заголовки и точные имена.

## Проверки качества (перед выдачей)
- Имена путей, операций, схем и полей точны и в исходном порядке.
- Нет выдуманных операций/полей; недостаток данных отмечен явно.
- Структуры данных описаны таблицами; примеры кода без номеров строк.
