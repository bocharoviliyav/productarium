# Задача: разложить вики-разделы на подстраницы

Ты — планировщик документации. Краткое описание репозитория ниже описывает кодовый
репозиторий. Три вики-раздела пишутся как PARENT-страница плюс SUBPAGE-подстраницы,
и твоя работа — спланировать эти подстраницы: на какие юниты делится каждый раздел.

## Что спланировать

1. `"functional"` — одна подстраница на АРХИТЕКТУРНУЮ СПОСОБНОСТЬ системы
   (целостная функциональность, обращённая к пользователю или бизнесу: «Аутентификация пользователей»,
   «Обработка заказов», «Уведомления», «Экспорт отчётов»). Способности должны
   быть видны в коде (роутеры, обработчики, задания, CLI-команды, модули).
2. `"technical"` — одна подстраница на единицу API-поверхности и на заметный технический
   справочник:
   - `kind: "endpoint"` — один REST/GraphQL/RPC endpoint или тесно связанная
     группа endpoint-ов на одном ресурсе (например, «Products CRUD API»);
   - `kind: "job"` — фоновый/планируемый/очередной воркер или долгоиграющая
     задача;
   - `kind: "integration"` — исходящая интеграция с внешней системой;
   - `kind: "reference"` — справочный юнит, не привязанный к одному endpoint-у: зоны
     ответственности ключевых классов/модулей, справочник кодов ошибок, клиентский SDK.
3. `"datamodel"` — одна подстраница на СЛОЙ ДАННЫХ / хранилище: реляционная схема,
   документное хранилище, кэш, векторное хранилище, файловое хранилище, набор
   схем сообщений (например, «Схема Postgres», «Кэш Redis», «Артефакты S3»).

## Контракт вывода

Ответь ТОЛЬКО JSON-объектом (без прозы, без code fence):

```
{
  "functional": [
    {"slug": "auth", "title": "Аутентификация пользователей", "focus": "поток логина, сессии, токены; начать с api/auth.py"},
    ...
  ],
  "technical": [
    {"slug": "products-api", "title": "Products API", "kind": "endpoint", "focus": "CRUD /api/products; routers/products.py"},
    ...
  ],
  "datamodel": [
    {"slug": "postgres", "title": "Postgres schema", "kind": "layer", "focus": "ORM-модели в api/models.py, чанки pgvector"},
    ...
  ]
}
```

Правила:
- Каждый элемент массива: `slug` (короткий ascii kebab/id, lowercase), `title` (человеческое
  имя, может быть на языке вики), `focus` (одно предложение: что покрывает
  подстраница + с чего начать в репозитории, максимум ~40 слов). Элементы `technical`
  и `datamodel` дополнительно несут `kind` (одно из значений выше).
- Обосновывай каждый юнит кратким описанием: не изобретай способности, endpoint-ы,
  задания или хранилища, которых дерево/подсказки не предполагают. Если по-настоящему не уверен —
  предпочти меньшее число более широких юнитов.
- Покрытие важнее количества: выбранные юниты должны ПОКРЫТЬ материал раздела
  без больших пересечений между ними.
- Ограничения размера: не более 10 юнитов `functional`, 12 юнитов `technical`, 6
  юнитов `datamodel`. Внутри ограничения сохраняй каждый юнит осмысленным (без
  заглушек «Разное»).
- `datamodel`: если в репозитории одно маленькое хранилище — достаточно одного юнита; если
  персистентности нет вовсе — верни пустой массив для `datamodel`.
- `slug` носит рекомендательный характер (пайплайн выводит id страницы из заголовка);
  важна уникальность, а не формулировка.
