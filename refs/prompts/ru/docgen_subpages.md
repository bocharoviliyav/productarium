# Контракты подстраниц docgen (парсятся в SUBPAGE_CONTRACTS)

Контракты содержимого для ПОДСТРАНИЦ родительских разделов (`functional`,
`technical`, `datamodel`). Парсятся при загрузке
`api.prompts._parse_subpage_blocks` в `SUBPAGE_CONTRACTS`
(subpage_type -> тело контракта). Пайплайн подставляет идентичность
элемента ({item_title}, {item_focus}, {item_kind}) и {siblings_list}
в задачу агента, собранную из `docgen_agent_section.md`; тело контракта
ниже встраивается дословно как «инструкция раздела». Контракты даны на
русском (язык ВЫВОДА управляется `docgen_agent_system.md`).

Формат: блоки `<subpage id="..."> ... </subpage>`, id:
`functional_item`, `technical_item`, `datamodel_item`.

<subpage id="functional_item">
# Подстраница: одна функциональная способность

## Цель
Исчерпывающее описание ОДНОЙ способности системы: её бизнес-процесс, код,
который её реализует, и её пределы. Эта подстраница — глубокое погружение, на которое
ссылается родительская страница «Функциональное описание».

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Обзор` — что способность даёт пользователю, задействованные
   актёры, точки входа (endpoint-ы/CLI/задания) и ожидаемый результат.
2. `## 2. Реализация` — модули и классы, реализующие способность,
   с их зонами ответственности; ключевые функции/методы с РЕАЛЬНЫМИ сигнатурами
   (проверь чтением); параметры конфигурации и фича-флаги, на неё влияющие.
3. `## 3. Бизнес-процесс (sequence)` — одна или несколько Mermaid
   `sequenceDiagram`, показывающие РЕАЛЬНОЕ взаимодействие для главного сценария:
   вызывающий → роутер/обработчик → сервис/домен → хранилище/внешние системы,
   с фактическими именами модулей/классов из кода.
4. `## 4. Активность (логика и ветвления)` — один или несколько Mermaid
   `flowchart` с явными узлами начала/конца, покрывающие логику решений:
   ветвления, циклы, альтернативные и ошибочные пути этой способности.
5. `## 5. Ограничения и граничные случаи` — поведение на краях: чего код
   НЕ обрабатывает, явные заглушки/TODO в этой области, известные
   ограничения, видимые в реализации.

## Правила
- Каждое утверждение цитирует `path` (с диапазонами строк, когда полезно); сигнатуры
  должны совпадать с кодом.
- Диаграммы должны отражать реальные цепочки вызовов, прочитанные из кода, а не
  выдуманные идеализированные потоки.
- Не описывай другие способности, кроме как однострочными перекрёстными ссылками
  на их подстраницы или соседние разделы.
</subpage>

# Подстраница: одна техническая единица (адаптивно по kind)

## Цель
Полная техническая спецификация ОДНОЙ единицы API-поверхности системы или
технического механизма. `kind` из твоей задачи выбирает вариант
контракта ниже.

## Контракт содержимого — kind "endpoint"
1. `## 1. Спецификация` — метод + полный путь, назначение, требования auth,
   характер sync/async/streaming, релевантная способность.
2. `## 2. Параметры` — таблица:
   `| Имя | Тип | Обязательный | По умолчанию | Источник (path/query/body/header) | Описание |`
   из фактического определения обработчика/роута и его моделей.
3. `## 3. Логика обработки` — пошагово что происходит: валидация,
   авторизация, бизнес-вызовы, побочные эффекты; условия ветвления —
   явно.
4. `## 4. Ошибки` — таблица `| Код/Статус | Сообщение | Когда происходит |`
   из фактических ошибочных путей в цепочке обработчика.
5. `## 5. Sequence-диаграмма` — Mermaid `sequenceDiagram`:
   клиент → роутер → сервис → хранилище/внешнее, реальные имена модулей.
6. `## 6. Activity-диаграмма` — Mermaid `flowchart` с началом/концом, покрывающий
   ветвления обработчика. Добавь Mermaid `stateDiagram-v2` ВМЕСТО, когда
   юнитом управляет машина состояний (заказы, задания, сессии).

## Контракт содержимого — kind "job"
1. `## 1. Спецификация` — что делает задание, триггер (расписание/очередь/событие/
   вручную), владеющий модуль.
2. `## 2. Логика обработки` — пошаговый пайплайн; потребляемые входы,
   производимые выходы, побочные эффекты.
3. `## 3. Надёжность` — идемпотентность, ретраи, поведение при прерывании
   (что происходит при краше посреди прогона), конкурентность/блокировки, обработка
   dead-letter — только реально присутствующие механизмы.
4. `## 4. Sequence / activity диаграммы` — реальная цепочка триггер→процесс→эффект;
   ветвления как `flowchart`, если они нетривиальны.

## Контракт содержимого — kind "integration"
1. `## 1. Спецификация` — внешняя система, назначение, протокол (HTTP/БД/
   очередь/SSE...), клиентский модуль.
2. `## 2. Аутентификация` — как клиент аутентифицируется (только механизм —
   никогда значения секретов).
3. `## 3. Обмен` — запросы/ответы/полезные нагрузки (формы, форматы),
   направление, частота/ритм, когда видно.
4. `## 4. Обработка сбоев` — таймауты, ретраи, фолбэки, circuit
   breaker-ы, маппинг ошибок как реализовано.
5. `## 5. Sequence-диаграмма` — реальный поток обмена.

## Контракт содержимого — kind "reference"
1. `## 1. Назначение` — что покрывает этот справочник и где он живёт в
   коде.
2. `## 2. Зоны ответственности классов/модулей` — таблица или список: имя,
   ответственность, ключевые методы, путь источника. (Для справочника кодов ошибок:
   `| Код | Значение | Где выбрасывается |`.)
3. `## 3. Паттерны использования` — как остальной код использует эти классы/
   коды, с 1-2 реальными примерами вызовов.

## Правила (все kind)
- Каждое утверждение цитирует `path`; параметры/ошибки/умолчания — из фактического
  кода, никогда из конвенций.
- Не дублируй таблицы родительской страницы; эта подстраница — ДЕТАЛИЗАЦИЯ.
</subpage>

# Подстраница: один слой данных

## Цель
Максимально детальная документация ОДНОГО хранилища/слоя данных: каждая сущность,
каждое поле, ограничения, индексы, миграции.

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Обзор` — технология хранилища, назначение, владеющие модули/
   клиенты, конфигурация подключения (только имена, никогда значения секретов).
2. `## 2. Сущности` — по каждой сущности/таблице/коллекции:
   `| Поле | Тип | Ограничения | По умолчанию | Источник |` — ВСЕ поля из
   определений моделей/миграций, включая индексы и ограничения
   уникальности (укажи их под таблицей или отдельным списком).
3. `## 3. ER-диаграмма` — Mermaid `erDiagram` сущностей и связей ЭТОГО слоя,
   с ключевыми атрибутами.
4. `## 4. Миграции` — история/инструментарий миграций слоя и заметные
   шаги эволюции схемы.
5. `## 5. Паттерны доступа` — кто пишет/читает этот слой, через какие
   модули; краткие перекрёстные ссылки на релевантные способности/API.

## Правила
- Поля/типы/ограничения — только из определений моделей/миграций.
- Пиши эту подстраницу только если код сервиса реально подключается к слою
  (клиент/DSN/конфиг в коде). Слой, видимый только в docker-compose/тестовых
  конфигах или в дайджесте баз продукта без ссылок в коде, не документируется.
- Очень широкие таблицы: перечисли все поля, но сожми аудит-колонки в
  одну строку («+ 12 аудит-колонок — см. `path`»).
- Нереляционные хранилища: опиши документы/ключи/схемы в эквивалентной
  табличной форме, когда возможно.
</subpage>
