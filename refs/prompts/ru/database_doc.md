# Задача: обзорная страница базы данных «{database_name}»

Ты — эксперт по реверс-инжинирингу баз данных. Напиши ОБЗОРНУЮ СТРАНИЦУ базы данных
для инженеров, исключительно (EXCLUSIVELY) на основе доказательств схемы, собранных её
инструментами интроспекции (MCP-сервер, подключённый к живой базе данных). Структуры
таблиц, индексы и связи рендерятся отдельными детерминированными страницами — твоя
страница описывает ОБЩИЙ уровень.

## Маскированная строка подключения

<masked_connection>
{dsn_masked}
</masked_connection>

## Детерминированный скелет (истина — здесь перечислены все схемы/объекты)

<skeleton>
{skeleton}
</skeleton>

## Сырые данные интроспекции (схемы → таблицы → определения → связи)

<schema_evidence>
{schema_dump}
</schema_evidence>

## Контекст продукта (дополнительный, НЕ доказательство схемы)

<product_context>
{product_context}
</product_context>

## Инструкции

Напиши Markdown ровно с тремя разделами:

1. **Обзор** — видимое назначение базы данных и её общая форма: домен, роль в
   продукте, количество схем и объектов, соглашения об именовании, характер
   нагрузки (OLTP/OLAP/смешанный) по форме таблиц и индексов.
2. **Раскладка схем** — пространства имён и то, что, судя по доказательствам,
   содержит каждое (по таблицам/вью/процедурам каждой схемы). Для одиночной
   схемы — логические группы таблиц вместо схем.
3. **Замечания по дизайну** — заслуживающие внимания проектные решения:
   ключи и их стили (суррогатные/естественные, GUID/последовательности),
   индексная политика, денормализация, аудит-поля, партиционирование,
   соглашения именования; на что смотреть при эволюции схемы.

## Напоминания

- НЕ выдумывай таблицы, колонки или ограничения, которых нет в
  доказательствах; помечай выводы явно как выводы (выведено из …).
- Контекст продукта — дополнительный источник смысла, но идентификаторы БД
  грунтуются ТОЛЬКО интроспекцией.
- Сохраняй идентификаторы таблиц/колонок ровно в том написании, которое
  используют доказательства.
- Не перечисляй все таблицы подряд — на этой странице общий уровень,
  детальные структуры живут на подстраницах.
- Пиши на языке {language_name} (технические термины — на английском).
- Никогда не включай учётные данные или полные строки подключения; маскированный
  DSN — единственное допустимое упоминание подключения.
- Твоё ФИНАЛЬНОЕ сообщение должно содержать ТОЛЬКО готовый Markdown-документ.
