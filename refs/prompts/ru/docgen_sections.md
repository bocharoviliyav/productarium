# Контракты разделов docgen (парсятся в SECTION_PROMPTS)

ОДИН файл с контрактами содержимого для всех 7 вики-разделов. Парсится при загрузке
`api.prompts._parse_section_blocks` в `SECTION_PROMPTS`
(section_id -> тело контракта). Блоки встраиваются в задачу каждого
сабагента раздела кодом `api.docgen.codebase`; язык ВЫВОДА управляется
`docgen_agent_system.md` (`{language_name}`); сами контракты ниже даны на русском
для русскоязычной локали промптов.

Разделы `functional`, `technical` и `datamodel` — PARENT-страницы: каждая
раскладывается на SUBPAGE-подстраницы по способностям / по API / по хранилищам, чьи
контракты живут в `docgen_subpages.md` (планируются через `docgen_decomposer.md`).
Контракт родительской страницы описывает только обзорно-агрегирующий слой и
перекрёстно ссылается на свои подстраницы.

Формат: блоки `<section id="..."> ... </section>`. Один блок на раздел,
id должны совпадать с `api.prompts.WIKI_SECTIONS`.

<section id="overview">
# Раздел: Общая информация (Overview)

## Цель
Опиши, ЧТО есть проект: назначение, технологический стек, ВСЕ архитектурные
способности, требования и структуру проекта. Это входная точка читателя
и вход для последующего анализа пробелов.

## Где искать в первую очередь
README*, манифесты пакетов (`package.json`, `pyproject.toml`,
`requirements.txt`, `go.mod`, `Cargo.toml`, `pom.xml`), точки входа
(`main.*`, `app.*`, `index.*`), конфигурационные файлы верхнего уровня.

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Название и краткое описание` — что делает проект, его главная цель,
   целевая аудитория (из README/манифестов; без маркетинговых выдумок).
2. `## 2. Технологический стек` — таблица:
   `| Категория | Технология | Версия (если указана) | Назначение | Источник |`
   Версии ТОЛЬКО там, где явно закреплены в манифестах.
3. `## 3. Возможности` — ВСЕ архитектурные способности системы, а не
   только ключевые: этот список — вход для анализа пробелов. Группируй, когда
   это естественно (ядро / поддерживающие / сквозные). Каждая способность: 1-2
   предложения + ссылки на реализующие файлы. Включай инфраструктурные и
   операционные способности (auth, кэширование, фоновые задания, интеграции,
   CLI, конфигурация, наблюдаемость), если они есть в коде.
4. `## 4. Системные требования` — кратко: среда исполнения (версия языка, ОС),
   требуемые сервисы (базы данных, очереди, внешние API), запросы/лимиты
   (порты, память/CPU, если указаны), особенности развёртывания.
5. `## 5. Структура проекта` — ключевые каталоги и их назначение (компактное
   дерево в блоке кода или небольшой Mermaid `flowchart`).
6. `## 6. Статус и лицензия` — только если есть в репозитории (версия,
   лицензия, ссылки на репозиторий/документацию).

## Правила
- Каждое утверждение о стеке/способностях требует цитаты `path`.
- Не выдумывай версии, зависимости или возможности.
- Сохраняй все 6 заголовков даже на маленьких репозиториях; сжимай описания вместо
  удаления заголовков.
</section>

<section id="architecture">
# Раздел: Системная архитектура (System Architecture, C4)

## Цель
Опиши архитектуру системы в нотации C4, выведенную ТОЛЬКО из
реального кода: точки входа, контейнеры, компоненты, актёров, внешние системы,
потоки данных.

## Где искать в первую очередь
Точки входа и файлы бутстрапа сервера, определения роутеров/API, связывание
dependency injection, клиенты внешних систем (SDK баз данных, очереди, HTTP-
клиенты), конфигурации развёртывания.

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Контекст (C4 Context)` — Mermaid-диаграмма `C4Context`: пользователи/роли,
   система, внешние системы, с которыми она взаимодействует.
2. `## 2. Контейнеры (C4 Containers)` — Mermaid-диаграмма `C4Container`: приложения,
   сервисы, базы данных, очереди; технология каждой; связи между ними.
3. `## 3. Компоненты (C4 Components)` — Mermaid-диаграмма `C4Component`, детализирующая ключевые
   контейнеры (пропускай, только если репозиторий действительно слишком мал для
   компонентов — тогда скажи об этом явно).
4. `## 4. Описания компонентов` — для каждого компонента: назначение,
   технология/фреймворк, ключевые файлы реализации, связанные API.
5. `## 5. Потоки данных` — основные потоки запросов/данных, очереди сообщений,
   API-интеграции.

## Правила диаграмм
- Каждый узел диаграммы должен соответствовать реальному модулю/файлу; цитируй файл рядом с
  каждым описанием компонента.
- Если синтаксис C4 недоступен в целевом рендерере, вырази ту же
  структуру через `flowchart`/`graph` — корректно отрисованная диаграмма важнее.
- Перекрёстно ссылайся на разделы «Общая информация» и «Технические детали» по заголовку
  вместо повторения их содержимого.
</section>

# Раздел: Функциональное описание (Functional Description) — родительская страница

## Цель
Карта способностей: ЧТО система делает для своих пользователей на обзорном
уровне. Детальное описание бизнес-процесса каждой способности живёт на её
собственной ПОДСТРАНИЦЕ (см. «Подстраницы»); эта страница агрегирует их и связывает
ссылками.

## Где искать в первую очередь
Определения роутеров/endpoint-ов, модули обработчиков/контроллеров, CLI-команды,
фоновые задания/воркеры, фича-флаги, списки возможностей из README.

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Карта возможностей` — ВСЕ функциональные способности, каждая 1-2 предложения:
   бизнес-ценность, актёры, точки входа (endpoint/CLI/задание). Покажи связи
   между способностями (какая какую использует/расширяет). Свяжи каждую способность с
   её подстраницей по заголовку.
2. `## 2. Матрица «актёр–способность»` — кто (роли пользователей, админы, сервисные
   учётные записи, внешние системы) какую способность использует, если это видно в коде.
3. `## 3. Ограничения и допущения` — ТОЛЬКО то, что явно присутствует в
   коде: заглушки, маркеры `TODO`/`FIXME`/`HACK`/`XXX`,
   `NotImplementedError`, замоканное поведение, задокументированные допущения в
   комментариях/докстрингах. Каждый пункт цитирует точный file:line. Без спекуляций.
4. `## 4. Подстраницы` — список подстраниц этого раздела (по строке на каждую:
   заголовок + что покрывает).

## Правила
- НЕ включай сюда use-case-диаграммы, user stories или нарративы бизнес-логики —
  они живут в подстраницах способностей.
- Упомянутые endpoint-ы/команды должны исходить из реальных регистраций роутов/CLI.
- Используй предоставленный список подстраниц дословно (заголовки и id страниц) при
  ссылках.
</section>

# Раздел: Технические детали (Technical Details) — родительская страница

## Цель
Инженерный обзор: полная API-поверхность, конфигурация, состояние
безопасности, обработка ошибок и кэширование. Детальные спецификации по endpoint-ам /
заданиям / интеграциям живут на ПОДСТРАНИЦАХ; эта страница агрегирует их и
даёт на них ссылки.

## Где искать в первую очередь
Конфигурационные файлы и загрузчики (`.env.example`, `config/*`, модули настроек),
настройка логирования, middleware, обработчики исключений, кэши, rate limiter-ы,
версии зависимостей в манифестах, lockfile-ы (суммаризируй, не вываливай целиком).

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. API-поверхность` — таблица ВСЕХ endpoint-ов (sync и async) и заданий:
   `| Метод | Путь/Задание | Назначение | Способность | Источник |` (только из определений
   роутов и регистраций воркеров). Помечай async/streaming
   endpoint-ы. Свяжи элемент каждой строки с его подстраницей, если она есть.
2. `## 2. Конфигурация` — ключевые параметры конфигурации и переменные окружения:
   `| Параметр | По умолчанию | Назначение | Источник |`. НИКОГДА не копируй ЗНАЧЕНИЯ
   секретов из файлов типа `.env` — только имена и назначения.
3. `## 3. Безопасность` — механизмы auth, обращение с секретами, ограничение путей,
   CORS, валидация входных данных как реализовано.
4. `## 4. Обработка ошибок` — стратегия ошибок, ретраи, фолбэки, dead
   letter queue, где присутствуют; сам справочник ошибок живёт в
   соответствующих подстраницах.
5. `## 5. Кэширование и производительность` — кэши, пуллинг соединений,
   лимиты конкурентности, пагинация — только механизмы, реально присутствующие
   в коде.
6. `## 6. Подстраницы` — список подстраниц этого раздела (по строке на каждую:
   заголовок + kind + что покрывает).

## Правила
- Никаких рекомендаций о том, что команде СЛЕДУЕТ делать — описывай то, что ЕСТЬ.
- Область отсутствует? Оставь заголовок с «Нет данных в предоставленном контексте».
</section>

<section id="cicd">
# Раздел: CI/CD и SRE (непрерывная интеграция, поставка и эксплуатация)

## Цель
Опиши реальный механизм сборки/развёртывания (кроме деталей тестирования — см.
раздел QA) плюс всё, что есть в репозитории по SRE: метрики, логи, трейсы,
health-чеки, алертинг, runbook/информация поддержки.

## Где искать в первую очередь
`.github/workflows/*`, `.gitlab-ci.yml`, `Jenkinsfile`, `azure-pipelines.*`,
`Dockerfile*`, `docker-compose*`, `Makefile`, скрипты сборки, конфигурации
релизов, helm/k8s-манифесты; код настройки метрик/логов/трейсов (middleware,
экспортёры, инструментация), health-endpoint-ы, правила алертов, дашборды.

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Пайплайны` — каждый пайплайн/воркфлоу: триггеры, стейджи, задания.
   Компактный Mermaid `flowchart` графа стейджей, когда их 3+.
2. `## 2. Сборка` — инструменты сборки, артефакты, кэширование.
3. `## 3. Контейнеры` — стратегия Dockerfile (мультистейдж, базовые образы),
   сервисы compose и их назначение.
4. `## 4. Развёртывание` — цели и механизмы деплоя (только из CI/CD-файлов и
   манифестов).
5. `## 5. Процесс релизов` — версионирование, теги, автоматизация релизов, если
   присутствует.
6. `## 6. SRE` — только то, что реально есть в репозитории, подзаголовками:
   `### Метрики` (экспортёры, счётчики, dashboards-as-code), `### Логирование`
   (формат, уровни, sinks), `### Трейсинг` (инструментация, сэмплеры),
   `### Health-чеки` (endpoint-ы liveness/readiness и что они проверяют),
   `### Алертинг` (правила алертов, уведомления), `### Runbook / поддержка`
   (дежурная информация, операционные процедуры, задокументированные в репозитории).
   Отсутствующие подобласти помечай явно однострочной пометкой «в репозитории
   отсутствует».

## Правила
- Цитируй файл воркфлоу/манифеста/инструментации для каждого утверждения.
- Отсутствующий CI: явно скажи, что отсутствует — не выдумывай пайплайн.
- Конфигурация тестирования в CI суммаризируется здесь только как стейджи пайплайна;
  сами тестовые наборы документируются в разделе QA.
</section>

# Раздел: QA — Тестирование (Testing)

## Цель
Опиши, как проект тестируется: фреймворки и раннеры, реально
представленная таксономия тестов, что действительно покрыто (из тестовых наборов и
CI-конфигов, а не из устремлений), фикстуры и фабрики, а также качественный
инструментарий вокруг тестов.

## Где искать в первую очередь
Каталоги тестов (`tests/*`, `test/*`, `*_test.*`, `*.spec.*`),
конфиги pytest/jest/go-test (`pytest.ini`, `pyproject.toml`,
`jest.config.*`, test-таргеты `Makefile`), шаги тестов в CI-воркфлоу,
fixtures/conftest, фабрики, конфиги покрытия (`.coveragerc`,
конфиги istanbul/nyc).

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Фреймворки и раннеры` — тестовые фреймворки, ключевые команды раннера
   (из конфигов/CI/Makefile), как запустить один тест.
2. `## 2. Таксономия тестов` — какие ТИПЫ тестов реально существуют
   (unit/integration/e2e/contract/smoke/load) и где каждый живёт;
   явная пометка для отсутствующих типов.
3. `## 3. Фактическое покрытие` — какие компоненты/потоки имеют тесты (сопоставь
   тестовые файлы с кодом, который они проверяют, по импортам и именам тестов), и
   заметные НЕПРОТЕСТИРОВАННЫЕ области («для X тестов не найдено») — детерминированные
   утверждения факта, без оценочных процентов.
4. `## 4. Фикстуры, фабрики и дублёры` — подготовка тестовых данных, билдеры,
   mock/stub/fake, тестовые базы/хранилища, герметичность (что набору
   нужно извне и что он мокает).
5. `## 5. Инструментарий качества` — измерение покрытия, линтеры, проверки типов,
   форматтеры, встроенные в тестовый/CI-поток, quality gates.

## Правила
- Каждое утверждение цитирует тестовый файл / конфиг / файл воркфлоу.
- Описывай, что тесты ДЕЙСТВИТЕЛЬНО проверяют (поведение под тестом), а не просто
  списки файлов.
- Никаких выдуманных чисел покрытия: сообщай только числа, заявленные артефактом
  репозитория.
</section>

# Раздел: Модель данных (Data Model) — родительская страница

## Цель
Всё, что система персистит, максимально детально: базы данных, схемы, ORM-
сущности, форматы хранения, схемы сообщений. Полная детализация каждого слоя данных
живёт на его собственной ПОДСТРАНИЦЕ; эта страница содержит обзор хранилищ,
карту сущностей между хранилищами и глобальный ER-вид.

## Где искать в первую очередь
ORM-модели, миграции (`migrations/*`, `alembic/*`, `prisma/*`),
файлы схем (`*.sql`, GraphQL/OpenAPI-схемы), классы сериализаторов/моделей,
коллекции документных хранилищ, полезные нагрузки сообщений.

## Контракт содержимого (заголовки Markdown в этом порядке)
1. `## 1. Обзор хранилищ` — таблица ВСЕХ используемых хранилищ:
   `| Хранилище | Технология | Назначение | Что там живёт | Источник |`
   (Postgres, SQLite, Redis, файлы, векторные хранилища, очереди), каждое со ссылкой
   на его подстраницу.
2. `## 2. Карта сущностей` — по каждому хранилищу: сущности/таблицы/коллекции, которые
   оно содержит, по строке на каждую (имя + назначение + источник). Полные списки
   полей живут в подстраницах.
3. `## 3. ER-диаграмма` — Mermaid `erDiagram` ГЛАВНЫХ сущностей и
   связей МЕЖДУ хранилищами (детальные диаграммы по хранилищам живут в подстраницах).
4. `## 4. Миграции` — инструментарий миграций и заметные шаги эволюции
   схемы.
5. `## 5. Потоки данных` — кто что пишет/читает (кратко; сошлись на «Архитектуру»
   для потоков).
6. `## 6. Подстраницы` — список подстраниц этого раздела (по строке на каждую:
   заголовок + слой + что покрывает).

## Правила
- Поля/типы — только из определений моделей/миграций.
- Документируй только хранилища, к которым КОД сервиса реально подключается
  (клиентские модули, строки подключения, конфигурация в коде). Хранилище,
  упомянутое лишь в docker-compose/тестовых конфигах или в блоке «Контекст баз
  данных продукта» без ссылок в коде, — НЕ слой данных сервиса: исключи его,
  одной строкой пояснив, что ссылок в коде нет.
- Нет базы данных в репозитории? Заяви это явно и опиши вместо неё формы данных
  конфигов/DTO, если они есть.
</section>
