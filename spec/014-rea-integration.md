# SPEC-014: Интеграция REA (reverse-engineering MCP)

Статус: planned · Волна 8 · Приоритет: средний

## Проблема

`rea` (github.com/morluto/rea, MIT) — MCP-сервер реверс-инжиниринга: нативные бинарники (Hopper/Ghidra/IDA CLI), Electron/JS-бандлы, .NET, WASM, EVM-контракты; запуск `npx rea-agents`, Node 22+. Потенциал — расширить database/codebase-анализ Productarium на скомпилированные артефакты. Однако платформенный MCP-полиси (`api/mcp/policy.py`) блокирует runners/интерпретаторы — `npx` почти наверняка попадёт под запрет, и админ не сможет подключить сервер штатно.

## Решение

Интеграция как исходящий MCP через существующую платформу (никакого кода REA в репо):

- Проверить совместимость команды запуска с полиси: если `npx` блокируется — задокументировать allowlist-вариант `node /abs/path/to/rea-agents` (node по абсолютному пути, без shell-раннера), при необходимости точечно расширив полиси одним явно документированным случаем (без ослабления остальных инвариантов).
- Пресет для админа: секция в README администрирования MCP с командой, требованиями (Node 22+, установленный REA), и какие тулы появляются после подключения.
- Hermetic policy-тесты: `npx`-запуск остаётся заблокирован (если решено блокировать), allowlist-путь — разрешён; никаких других новых разрешений.
- Аутпут REA-тулов проходит те же санитайзеры/гейты, что и прочие MCP-результаты (ничего нового — только тест-подтверждение).

## Критерии приёмки

- Policy-тесты покрывают оба варианта запуска; security-инварианты полиси не ослаблены (все текущие policy-тесты зелёные).
- Документация позволяет админу подключить REA за один шаг без правки кода.

## Затрагиваемые файлы

`api/mcp/policy.py` (минимально, если нужно), `api/tests` policy-тесты, `README.md` или `docs/` (секция MCP-пресетов), `api/routers/mcp_admin.py` (только если пресет требует).
