# SPEC-003: Устойчивость фронтовых запросов («Failed to fetch»)

Статус: planned · Волна 1 · Приоритет: низкий (баг не критичный)

## Проблема

На дашборде (список продуктов) и странице продукта периодически всплывает браузерный `TypeError: Failed to fetch` (нативная ошибка `fetch`: сеть/abort/CORS), хотя приложение продолжает работать. Прямых вызовов без обработки в этих экранах — поллинг списков/джобов.

## Решение

1. Единый fetch-клиент `src/lib/api.ts` (обёртка над `fetch`):
   - `AbortController` + таймаут;
   - ретраи только для идемпотентных GET (2 доп. попытки, экспоненциальный backoff);
   - `AbortError` при размонтировании компонента/навигации — молча (не ошибка);
   - сетевые/5xx фейлы GET — тихий ретраи-режим, после исчерпания — ненавязчивый toast/индикатор без блокировки UI.
2. Перевести на клиент: `src/app/page.tsx` (дашборд-поллинг), `src/app/products/[productId]/page.tsx` (поллинг активных джобов), далее по мере (`admin/page.tsx`).
3. Диагностика: логировать фейлы (URL, статус/тип ошибки) в консоль с единым префиксом `[api]`; проверить таймауты прокси в `next.config.ts` (rewrites на :8001).

## Не-цели

- SSE-поток чата (там своя логика reconnect), офлайн-режим, кэширование.

## Критерии приёмки

- Ручной тест: кратковременный рестарт бэкенда (3–5 с) не показывает необработанную ошибку на дашборде/странице продукта; после восстановления данные обновляются.
- `bun run lint`, `bun run build` зелёные.

## Затрагиваемые файлы

`src/lib/api.ts` (новый), `src/app/page.tsx`, `src/app/products/[productId]/page.tsx`, `next.config.ts` (проверка), прочие `src/**` по мере перевода.
