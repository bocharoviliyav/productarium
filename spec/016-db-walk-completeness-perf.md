# SPEC-016: Полнота и скорость обхода больших схем БД

Статус: planned · Волна 7 · Приоритет: критичный

## Проблема

Подтверждённый root cause (код): на схеме из 836 таблиц UI видит только ~51 таблицу (обрыв на букве «A»); схема из 98 таблиц обходит целиком; база 5ТБ анализируется ~4 суток.

1. **Тихий ранний стоп пейджинга**. `_paged_rows` (`api/docgen/database.py:2001`) останавливается, когда страница приходит «короткой» (`len(chunk) < page_rows` → break). Но страница режется не базой, а чар-капом менеджера MCP: `_ORA_PAGE_ROWS=1200` (строка 756), рендер строки колонок ~115+ символов → страница ~1200×115≈138k символов превышает кап ~100k; `_call_tool` обрезает ответ с маркером `…[truncated` (`api/mcp/manager.py:589-591`), парсер видит ~800–850 строк < 1200 и делает вывод «данные кончились». `ORDER BY table_name` — обрыв стабильно на ~51-й таблице. Ни ошибки, ни предупреждения — тихая неполнота.
2. **Нет сверки с ожидаемым количеством.** `COUNT(*)` перед обходом не делается, поэтому расхождение «запрошено N — получено M» никого не насторожило.
3. **4 суток на 5ТБ.** Полные чтения данных нет (`db_lookup`/`entity_source` читают только интроспектированный каталог), время съедают 836 LLM-сабагентов deep-units без чекпоинтов прогресса и без сэмплингового режима «первых строк».

## Решение

- **Chop-detection + дробление страницы**: после каждого `fetch` проверять маркер `…[truncated` в сыром ответе и сравнивать спарсенные строки с ROWNUM-окном; при чопе — halving страницы (1200→600→300…) и повтор ТОГО ЖЕ окна, пока страница не влезет в кап целиком; обход продолжается до настоящего конца (последняя страница < page_rows БЕЗ маркера чопа). Функция page_rows адаптивная (стартует консервативно, может расти на мелких схемах — опционально).
- **COUNT(\*)-обёртка**: перед bulk-walk берём `COUNT(*)` для каждого каталог-запроса; после обхода fetched vs expected попадает в errors/coverage (`_coverage_section`), расхождение — WARNING в лог.
- **Coverage-отчёт per-query**: fetched/expected/chopped — уже частично есть на overview, расширить до per-query статистики.
- **Сэмплинг первых строк для deep-units** (опциональный гейт): для юнит-агентов таблиц достаточно `FETCH FIRST 5 ROWS`/`ROWNUM<=5` выборки — интроспекция на пустой базе быстрее и полнота не страдает; подтверждено, что полные чтения таблиц не делаются — это ускорит evidence-бандл и снизит таймауты. Гейт/бюджет настраиваемый.
- **Прогресс-чекпоинты deep-units**: для 800+ объектов сохранять промежуточный прогресс (какие юниты готовы) — при рестарте джобы/отмене не терять работу; прогресс в jobs state.
- Логирование: chop-события с размером страницы и номером — видимость вместо тишины.

## Критерии приёмки

- Unit-тест: мок 836 таблиц (строки колонок ~115 символов, тул обрезает на 100k) — собираются ПОЛНОСТЬЮ (все 836 в pages/coverage), в логе chop-события.
- Unit-тест «обрезанная страница → дробление и продолжение»: первая страница чопнута → halving → полный сбор.
- Регресс скорости малых схем отсутствует (существующие тесты обхода зелёные, без новых тяжёлых запросов при малых COUNT).
- COUNT-сверка: мок с ожидаемым 100/получено 60 (чоп) → coverage показывает расхождение.
